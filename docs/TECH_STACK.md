# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, so each query is written once for both databases. With `DATABASE_URL` in its environment it uses the Supabase Postgres database through the session pooler, with every table in the `undercover` schema and at most 4 connections, waiting up to two minutes for one; otherwise SQLite, as in the tests. `main.py` holds the app and the claim, document and handler operations; `runs.py` (dispatches and evaluations), `configuration.py` (the claim agent's versions), `rounds.py` (rounds of improvement, their proposals and the recipe's versions) and `platform_settings.py` (the settings and the models allowed) are `APIRouter`s; they share the `Database` dependency in `dependencies.py`, what they look up in `lookups.py`, the claim views in `views.py` and the run views in `run_views.py`, and none imports another. `auth.py` checks the signed-in handler against Supabase Auth's public keys at `VITE_SUPABASE_URL` with PyJWT; `judge.py` calls Jev through OpenRouter's Decisions endpoint at `OPENROUTER_URL`; `new_runs.py` records a new run for `runs.py` and `rounds.py`, `documents.py` splits the documents into sections, `verdict.py` is UnderCover's rule for keeping a version, `spending.py` what a round has spent, `diffs.py` the lines two texts differ by, and `improver_view.py` what the improver reads. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The payout rules are in `backend/payout.py`, and the scoreboard's measures in `backend/scoring.py`. The backend calls the agent's service after a sign-off, to start a dispatch, an evaluation or a round, and to pass on a decision on a proposal, at `UNDERCOVER_AGENT` in the environment or `http://127.0.0.1:8002`.
- `agent/`: six parts. `api.py` is the claim agent's and the dispatcher's way to the backend: claims, runs, its version, the documents, the payout rules and the records of cost and time, with nothing that reads the scores or the handlers' decisions. `improver_api.py` is the improver's, under `/api/runs/rounds`, with the round as the dashboard reads it. `models.py` builds the chat models through OpenRouter for both. Both send their requests through `client.py`, the one client, at `UNDERCOVER_API` or `http://127.0.0.1:8000`. `improver.py` is the improver, a LangChain `create_agent` on GPT-6 Luna at medium reasoning effort, with the lab's four tools, `HumanInTheLoopMiddleware` on its two proposals, `ModelCallLimitMiddleware`, hooks that stop it with its round, turn off parallel tool calls and record each call's cost, and a `PostgresSaver` of its own. `tools.py` holds the claim agent's tools, the context they read and the claim graph's state, and the tools that act on the claim read it from the agent's context through `ToolRuntime`. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch or an evaluation. `service.py` is the agent's service, a FastAPI app the backend calls to start a dispatch, an evaluation or a round, to pass on a decision on a proposal and after a sign-off, with only one dispatch, evaluation or stretch of a round's work at a time; in the cloud the agent runs as a service like this. `console.py` sets up the report lines and says in one line what went wrong.
  - The claim agent is a hand-written LangGraph `StateGraph`, built by `claim_graph(llm, instructions, saver)` from a version of the configuration: a node that calls the model, a `ToolNode`, a pause for a sign-off with `interrupt()`, and a node that pays. Its nodes record each reply, tool call, tool result and section read on the claim, and each model call's tokens and cost, return refusals to the model and limit the model calls. It saves its state after every step with LangGraph's `PostgresSaver` in the same Supabase database, with `durability="sync"`, so the agent always needs `DATABASE_URL`, even when the backend runs on SQLite. Each claim run gets a saver of its own on the process's shared `ConnectionPool` of at most 4 connections, since a saver lets one claim at a time read or write. The agent is synchronous throughout, because async Postgres connections don't work with Windows' default event loop.
  - The dispatcher is a LangGraph `StateGraph` with no model, in the style of `labs/week2day4.ipynb`: `list_claims` lists the claims, `fan_out` sends each to the `work_claim` node with a `Send`, `max_concurrency` caps the claim agents at once at N, and `finish_run` runs once after them all. The `work_claim` node has a `RetryPolicy` for rate limits and timeouts. It saves no progress of its own.
  - The harness's entry points are `work_claim(claim_id, run_id, graph)`, which works one claim as a new attempt, `carry_on(claim_id, run_id, graph)`, which carries a claim on from its saved progress, and `work_in_run(claim_id, run_id, new_graph)`, the one function the dispatcher calls, which does either on a graph of its own. Each times its spells of work and records them with their run.
  - Every claim graph run is traced in Langfuse, in a session named after the claim and its thread, and tagged with its run's id in `langfuse_tags`, and in a round's evaluation with the round's id too; the improver's work in a round is one session, `Round N:<round id>`.
  - It uses the model and reasoning effort of its run's version, `openai/gpt-6-luna` at low for version 1, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort, recorded as `default`. Each model call's cost comes from OpenRouter's `usage.cost` on the reply. The backend's address is `UNDERCOVER_API` or `http://127.0.0.1:8000`. Like the dashboard, `uv run -m agent` reads it from the shell's environment, never `.env`; the agent's service gets `.env` from `npm run dev`.
- `dashboard/`: React, Vite and TypeScript. `api.ts` is its only way to the backend and `supabase.ts`, with `@supabase/supabase-js`, its only way to Supabase Auth, reading `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, which Vite takes from the root `.env` in development only. Charts are drawn in SVG, with no library.
- `e2e/`: Playwright tests, with stand-ins for the agent's service, Supabase Auth and the judge.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Supabase session pooler connection string (`DATABASE_URL`), the Langfuse keys (`LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`), the Supabase project's address and publishable key (`VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`) and the handlers' password for the browser checks (`HANDLER_PASSWORD`).
